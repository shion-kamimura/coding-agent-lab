# 開発手順

環境準備、変更に応じた検証、文書更新、PR、結果報告、中断再開の正本です。
共通の作業境界と資料への入口は [AGENTS.md](../AGENTS.md) に置きます。
この手順は開発を支援する人・AI向けで、製品のCoding Agentの実行権限や
承認・隔離を実装するものではありません。

## 1. 目的と作業状態を確認する

依頼と対象Issue/PRを読み、解決する課題、期待する動作、対象・対象外、
確認可能な受け入れ条件、検証方法を確認します。
新規タスクは [Issueテンプレート](../.github/ISSUE_TEMPLATE/development.md) を使い、
入力・操作と期待結果を具体化します。調査のみなら回答に必要な根拠を定めます。

```bash
git status --short --branch
git rev-parse HEAD
git diff
git diff --cached
```

現在のブランチ・SHAと人の変更を把握し、新規変更は専用ブランチ、PR修正はその
headで進めます。ベースブランチの更新状況も確認します。目的が不明な変更を
取り込んだり破棄したりせず、依頼と差分を対応させます。

## 2. 必要な環境を準備する

Pythonコードの実行・品質チェックにはPython 3.15の最新パッチ版を使います。
最低対応版は3.15で、CIも3.15を検証します。3.14以前は対象外です。
読取調査や文書・テンプレートのみの変更には、依存インストールは必須ではありません。

```bash
git clone https://github.com/shion-kamimura/coding-agent-lab.git
cd coding-agent-lab
python3.15 -m venv .venv
source .venv/bin/activate
python --version
python -m pip install --upgrade pip
python -m pip install -e '.[dev]'
```

既存のチェックアウトではcloneを省略します。Windowsでは対応版Pythonで
`py -3.15 -m venv .venv` を実行し、PowerShellで
`.venv\Scripts\Activate.ps1` を使って有効化します。

依存と品質ツールの設定は [pyproject.toml](../pyproject.toml) が正本です。
venv・pipとバージョン範囲による依存管理を維持し、ロックファイルは未導入です。
環境不足や接続・権限エラーは、原因と未実行項目を記録します。
必要な環境を準備できるまで、依存する検証を成功扱いにしません。

通常テストはAPIキー・外部通信・API料金なしで実行します。
実際のAPIへの接続やモデルの回答品質は、通常テストでは検証できません。
APIキーなどの秘密情報はコミットしないでください。[.env.example](../.env.example) は
説明用で、`.env`の自動読み込みは未実装です。実APIを利用するときは環境変数として
設定します。API利用料が発生する呼び出しの例と設定方法は
[LLM Clientの利用ガイド](llm-client.md) を参照してください。
開発環境や依存管理の選定理由は [ADR 0001](adr/0001-project-foundation.md) にあります。

## 3. 変更の影響に応じて検証する

関連する仕様・コード・既存テストを読んで小さく変更し、受け入れ条件に対する
証拠を選びます。正常系・失敗系のテスト追加を全タスクへ一律には要求しません。

| 変更・作業 | 選ぶ検証 |
| --- | --- |
| 機能追加 | 入力・操作と期待結果を確認するテスト。該当する失敗系も含め、影響する品質チェックを実行 |
| 不具合修正 | 再現条件と修正後の期待結果を確認。必要な回帰テストと影響する品質チェックを実行 |
| 依存・パッケージ・CIなど広い影響 | 下記の品質チェック一式とwheelのビルド・インストール後のテスト。workflowの条件・設定も照合 |
| 文書・テンプレートのみ | 記述と実装・設定の整合、関連するローカルリンク、テンプレートの記入可能性、差分をレビュー |
| 調査のみ | 根拠となるコード・資料・観測を確認し、結論と未確認事項を区別 |

Pythonコードの品質チェックは次のとおりです。小さな変更では影響範囲に合うものを
選び、pytestは必要なら対象ファイルやケースを指定します。

```bash
python -m ruff check .
python -m ruff format --check .
python -m mypy
python -m pytest
```

自動整形は `python -m ruff format .`、修正可能なlintの適用は
`python -m ruff check --fix .` です。自動修正後も差分を確認します。

wheel検証は [CI](../.github/workflows/ci.yml) と同じく、ビルドしたwheelを
インストールしてpytestを実行します。ローカルでは古い成果物が混ざらない空の
出力先を使います。以下はBashで、有効なvenvのeditableインストールを置き換えます。

```bash
wheel_dir=$(mktemp -d)
python -m pip wheel . --no-deps --wheel-dir "$wheel_dir"
python -m pip uninstall -y coding-agent-lab
python -m pip install --no-deps "$wheel_dir"/*.whl
python -m pytest
# 開発を続ける場合はeditableインストールへ戻す
python -m pip install -e '.[dev]'
```

各コマンドの成功を確認してから次へ進みます。Windowsでは空の出力先を用意し、
生成されたwheelのパスを指定して同じ検証を行います。

文書だけの変更に無関係な製品テスト・API呼び出しや文言一致テストを追加しません。
専用の環境診断・Markdownリンク検査・ハーネス評価基盤も現段階では追加しません。
失敗時は今回の変更、既存不具合、環境不足、テスト側の誤りを切り分け、
コマンドと結果、対象SHA、未コミット変更の有無を記録します。

## 4. 関連文書と差分を確認する

READMEへ追加する基準は「初めて訪れた人が、プロジェクトを理解して次へ進むために必要か」
です。短い説明とリンクを載せ、詳細は次の正本へ集約します。同じ手順を重複させません。

| 内容 | 配置先 |
| --- | --- |
| 概要、現在の状態、ドキュメントへの案内、ライセンス | [README](../README.md) |
| AIの共通ルールと作業別の入口 | [AGENTS.md](../AGENTS.md) |
| 学習を支援する進め方、説明の到達目標、教材と確認日 | [学習の進め方](learning.md) |
| 環境構築、検証、PR・結果報告、中断再開、秘密情報の扱い | この開発手順 |
| LLM Clientの利用例、設定、使用量、エラー | [LLM Client](llm-client.md) |
| ディレクトリ構成、モジュールの責務、実装順序 | [アーキテクチャ](architecture.md) |
| 技術選定の理由、依存管理・ロックファイルの判断 | [ADR](adr/) |
| 実験の記録方法、評価結果、再現手順 | [実験の記録](../experiments/README.md) と各実験の記録 |
| CIジョブ、ルールセットの設定手順 | [CIとマージ条件の設定](ci.md) |
| 作業の計画・進捗、受け入れ確認、検証結果、引き継ぎ | 対応するIssue・PR |

重要な判断を追加・変更するときは、背景・決定・代替案・影響をADRに残します。
計画・進捗・受け入れ確認・引き継ぎはIssue/PR本文・コメントに残し、
Issue/PR単位の進捗ファイルをdocsへ複製しません。

PR前に関連文書を実装と揃えて同じ差分へ含めます。更新不要なら理由をPRに記載し、
PR修正で動作や判断が変わった場合も追従します。
関連するローカルリンクの参照先・アンカー、コマンド、実装済みと今後の計画の区別を
確認し、`git diff --check` と差分レビューで依頼範囲・受け入れ条件に照合します。
移動・分割時は参照元のリンクも更新します。CLIが利用可能になった段階で、READMEへの
最小の利用例の追加を検討します。

## 5. PRと結果報告

変更を専用ブランチへcommit・pushし、[PRテンプレート](../.github/pull_request_template.md)
に従って問題、変更後の動作、設計理由、受け入れ条件への対応を説明します。
Issueをすべて満たす場合のみ `Closes #番号`、一部対応なら `Refs #番号` を使います。
調査のみ・ローカル作業のみなど依頼の指定を優先します。

検証は実行したコマンドと結果、対象SHAを記載します。未コミット状態での検証は
その旨を明記し、未実行・未検証と理由を分けます。ローカルの自己テストと
GitHub ActionsのCIは別の実行です。CIは対象SHAとChecks/ActionsのURLを確認し、
待機中・失敗・未確認を成功と記載しません。修正後は新しいSHAに対して確認します。

CIの構成・実行条件とマージ条件の設定手順は [CIの設定資料](ci.md) を参照してください。
文書のみのPRでも現在のCI設定に従いますが、ローカルで製品テストを一律に要求する
意味ではありません。CIの実行条件とマージ条件は別で、Rulesets・branch protectionの
実設定はこの手順の対象外です。PR作成・CI成功はマージの許可を意味しません。

完了報告には、変更と受け入れ条件の対応、実行した確認と結果、PR、対象SHAのCI、
未検証事項・制約・残作業を含めます。今回の手順導入だけで開発効率が改善したとは
判断せず、実作業の手戻り・人の介入・検証漏れを見て手順を追加・削減します。

## 中断と再開

中断時はIssue/PRに次を残します。書き込みできない場合は回答に記載します。

- 目的と対象Issue/PRへのリンク
- branch、開始・現在のSHA、未コミット変更と保持すべき人の変更
- 完了した作業、残作業、判断と関連資料
- 実行した検証と結果、未実行・未検証事項、対象SHAのCI
- 停止理由と次に行う具体的な操作

再開時はIssue/PRの最新記録を読み、branch・SHA・status・差分を実際の状態と照合し、
必要な環境を確認します。記録とheadが違う場合は差分を調べ、過去の成功をそのまま
流用しません。記録や接続が不足する場合は不足と進められる範囲を示し、
不明点に依存する変更を推測で進めません。
