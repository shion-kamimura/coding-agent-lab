# アーキテクチャ

## 目的と現在地

Agent EngineeringとLLMOpsを学ぶため、単一のCoding Agentを段階的に実装します。
現在は開発環境と、Claude Messages APIを使う同期テキスト生成のLLM Clientを実装しています。
既定はHaikuで、同じ呼び出し側から設定でSonnetへ手動で切り替えられます。
CLI、Agent Loop、ファイル操作、コマンド実行は今後の設計案です。

## 最初の到達点

自然言語の指示をCLIで受け取り、作業ディレクトリのファイルを調査・修正し、
テスト結果を確認するエージェントを目指します。

```text
CLI → Agent Loop → LLM Client → モデルAPI
          ↓              ↑
       Tool実行 → 結果を履歴へ追加
```

| モジュール | 責務・実装状況 |
| --- | --- |
| `cli.py` | 引数、表示、終了コード |
| `agent.py` | 会話状態、反復、終了条件、実行予算 |
| `llm.py` | 実装済み：メッセージ・応答・使用量の型、ClientのProtocol、共通例外 |
| `anthropic_client.py` | 実装済み：Claude Messages APIとの変換、設定、エラー変換 |
| `tools/filesystem.py` | 作業ディレクトリ内の読み書き |
| `tools/execution.py` | 許可されたテストの実行、時間制限、結果取得 |

未実装のモジュールは必要となるIssueで追加します。LLM ClientはProtocolで差し替え
可能にし、テストでは実際のAnthropic SDKと模擬HTTP通信を使って検証します。
通常テストにAPIキー・外部通信・API料金は不要です。実APIの疎通やモデル品質は未検証です。
Clientの契約は会話履歴から完成したテキストを返すところまでで、Tool Calling、
ストリーミング、Agent Loopの履歴管理は後続で拡張します。

## 現在のLLM Clientの境界

- SDKの生成・認証と接続の終了は呼び出し元が担当し、ClientはSDKを受け取る。
- 設定は`AnthropicConfig`にまとめる。HaikuとSonnetの自動振り分けやフォールバックは行わない。
- 推論はadaptive、effortはmedium、出力上限は推論を含めて16,000トークンを既定とする。
- 通信タイムアウトは30秒、再試行はSDKだけで最大2回とし、設定で変更可能にする。
  全体の実行時間や費用の上限を保証する値ではなく、長い実応答での適切な時間は未検証。
- 完成したテキストだけを返す。打ち切りと拒否は別の共通例外に変換し、使用量などを保持する。
- 使用量は推論とキャッシュの区分を保持するが、料金の計算・予算の執行は行わない。

Haikuの性能が将来の全作業に十分とは判断していません。Agent Loopの実装段階で、
小さなコード課題を10〜20件程度用意し、HaikuとSonnetの成功率、成功1件あたりの総費用、
完了時間、反復回数、人の手直し量を比較します。この評価基盤は今回の実装に含めません。

## 後続実装で決める境界

- ファイル操作は作業ルート外への移動とシンボリックリンクによる逸脱を検証する。
- モデルの出力とリポジトリ内のテキストを信頼せず、ツール側で引数と権限を検証する。
- 変更・コマンド実行に対する承認方針を実装前に決める。
- コマンド実行の隔離方法、許可するコマンド、タイムアウトを決める。
- 反復回数、トークン、費用、API再試行に上限を設ける。
- ログにはAPIキーや機密ファイルの内容を残さない。

## 段階的な実装順序

1. 開発環境の初期化（実装済み）
2. LLM Client：プロバイダー選定、型、エラーと再試行方針（同期テキスト生成を実装済み）
3. File Tools：作業ルート制約と正常系・失敗系テスト
4. Agent Loop：Tool Calling、履歴、停止条件、予算
5. CLI統合：利用手順、偽のLLMによるE2Eテスト
6. LLMOps実験：トレース、評価セット、コスト・品質の比較

技術選定の理由は [ADR 0001](adr/0001-project-foundation.md) と
[ADR 0002](adr/0002-llm-client.md) に記録します。
